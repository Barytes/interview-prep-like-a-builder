### 问答中的三类反馈，以及与 teach 的比较

用户特别关注作者补充现实约束、指出不对劲的过程，并要求与 teach 技能比较。已完整读取该技能。

三类动作：
1. 补知识：问概念、机制、数值例子；与 teach 明确要求高度重叠。
2. 检查解释：如两类客户的模拟需求变化都为 15%，不能支持“反应不同”的解释，要求修正模拟。
3. 修改工作方案：如质疑 accounts → sessions → minutes 的复杂度/误差，改成 accounts → minutes；暂不预测 profile 级行为；pause ads 单独处理；要求各团队独立预测后协调。

比较结论：
- teach 不是只能讲知识/出题；它明确支持 Mission、可信资源、小课、真实步骤、交互练习、模拟器、学习记录及外部实践。
- 它最明确维护的是学习状态与下一步教学；作者的反馈还持续修改业务假设、问题范围和系统设计。
- 当前 teach 没有明确强制维护一个贯穿课程、持续接受检查与修订的工作系统。可以把这种要求补入，但尚未获授权修改。
- 作者对新领域不熟，但已有可迁移的工作经验。初学者需要教学 Agent 主动呈现关键约束、反例、可检查的结果，并逐渐培养用户自己提问和判断的能力。

## 建议与未决事项

下面是助手建议，尚未被用户采纳为计划：

1. 先选一个具体、值得试两周的岗位目标；逐步形成职业判断。先比较 3–5 个真实岗位，再选一个公司/团队/岗位作为主要对象，其余做参照。数量与时长是建议，不是已约定的预算或期限。
2. 比较岗位时看产品用户、日常工作/交付物、实际困难、进入条件，以及能否找到可练习的核心任务。不能只读技术栈或以公司名气替代判断。
3. 以工程文章、设计讨论、故障复盘、issue/PR 学习“问题 → 尝试 → 失败 → 修正 → 验证”。区分来源事实、推断、练习假设。
4. 围绕一个真实用途，先手工完成工作，再构建最小系统。任务结果用于发现约束，知识学习由具体阻碍牵引。
5. 通过原文核对、测试、实际使用者或从业者反馈检查结果；AI 可以提出解释，但独立证据负责纠正解释。
6. 将岗位探索与工作模拟结合：候选岗位 → 核心小任务 → 学习/交付 → 外部反馈/修订 → 重新评估岗位。

最值得继续的分支：
- 用户想先选方向/岗位：核对当前约束和真实 JD，收敛到具体工作；别把 Agent 或 Research Scientist 直接当成已选方向。
- 用户想完善学习流程：将“业务约束/假设、系统设计、例子验证与修改记录”融入 teach，先明确期望流程再按授权实施。
- 用户想继续理解案例：回到共享会话对应轮次，先讲一个具体机制和例子，再让用户判断。
